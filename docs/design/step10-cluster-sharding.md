## 1. 为什么集群分片现在只做规划

- **当前形态是单写主库**（SQLite 单写 + WAL + litestream 复制）。分片的前提是"多个可写分片"，与单写边界互斥；过早分片会把原子发布、CAS、内容哈希、QUG、发布状态机全部撕碎。
- **远期 HA 走 rqlite 模式**（WAL 兼作 Raft log）。Raft 提供的是"同一份数据的多副本 + 选主"，与分片（把数据按 key 拆到不同节点）是正交的两条轴。规划须明确二者的衔接，避免把复制当分片、把分片当复制。
- 数据规模：千级页面、万级 SKU/事实。单机 SQLite + qdrant 完全够用，分片的动机（承载力/吞吐/超大规模）尚未被需要。

因此：#10 的"集群分片"在本 Step 收敛为一份**可执行的演进路线文档**，标注为"设计规划"，不占实现验收。

## 2. 分片是什么、不是什么（边界澄清）

不是：
- 不是多副本/主从（那是 Raft / litestream 的职责：同一份数据多处存，容灾 + 读扩展）。
- 不是把 qdrant 换分布式（qdrant 本身可多机分布；Wiktor 的 SQLite 事实/知识平面是权威，向量是派生索引，理应不共享分片）。

是：
- 把**事实/知识平面的数据**按分片键拆到多个可写 SQLite 分片（shard），每个分片独立单写；单一全局查询需合并各分片结果。
- 召回侧：向量检索在 qdrant 集中做候选召回 + 全局过滤，SQLite 分片只承担页面/事实的权威存取——因此分片的主要暴露面是**写入**（编译发布）与**点查/按 entity 取回**，而非全文检索。

这一不对称（向量集中、SQLite 分布）是本规划的核心观察，直接决定分片键与路由。

## 3. 分片键（shard key）选择

候选与维度（entity_id / domain / 写入热点 / 原子性）：
| 键 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| `domain` | 天然隔离领域包；原子发布（编译/发布/QUG）都在单 domain 内，天然同片 | 单 domain 仍可能超单机 | 首分键 |
| `entity_id` 哈希 | 均匀分布、承载力线性扩展 | 拆散同一 domain/同一发布事务；原子性被撕碎 | **不作为首分键** |
| `entity_id` 范围 | 相邻实体同片 | 热点偏斜、均衡难 | 不采用 |

**决策：分片键 = `domain`（一级）＋ 必要时 `entity_id` 哈希作二级分片**。理由：Wiktor 的原子单元是"一个 domain 的一次编译发布"（页面/评分/FTS5/事实在同一 SQLite 事务 + qdrant 两段同步），把同一 domain 的所有数据放同一分片，原子性、CAS、QUG 发布、内容哈希全部保持不动。只有当单个 domain 超出一台机器承载时，才在 domain 内按 entity_id 哈希再分，并接受"该 domain 的发布需跨片协调"的复杂度跃升（见 §6）。

## 4. 路由（routing）

- 写路由：`server` 收到请求 → 由 `shard_key(domain)`（或 domain+hash）映射到分片连接——一张**静态 or 动态分片映射表**（`domain → shard`）。
- 读路由：全文/向量召回在集中侧（qdrant）完成，返回命中实体 → 按命中实体的 domain 再回各自分片取权威页/事实；也可在分片各自跑 `QueryEngine` 后合并。
- 两种合并策略：
  - **集中召回 + 分片取回**（推荐）：qdrant 先给 top-k 候选（含 domain），再按 domain 并发取分片。控制结果数、避免全量广播。
  - **分片广播 + 归并**：每个分片本地跑检索，RRF/评分归并。适合"每个分片必含结果"的查询，代价是 N 倍查询。

## 5. 重平衡（rebalance）

- 分片是**逻辑层**：`domain → shard` 映射表由中心元数据（可存在一个"目录分片"或在未来 Raft 元数据）管理。
- 重平衡 = 迁移一个 `domain` 的整份数据（SQLite 文件/WAL + 重放）到另一分片，然后原子切换映射表。因为迁移单位是"整个 domain"，不需要跨行的数据搬移，重平衡即"整库快照 + 增量追平 + 指针切换"，复杂度低。
- `generation/epoch` 已用于内容哈希与发布版本，可复用作迁移的版本锚点：迁移期间冻结写入（或双写追平），epoch 对齐后切换。

## 6. 跨片一致性（跨 domain 关联查询的边界）

- **不跨片事务**：保持"单事务原子发布"仅在同一 domain 内；所有聚合/关联合并都在查询侧而非写入侧。文档须明言：跨 domain 的参照完整性由上层（领域包）保证，SQLite 不在多片间做分布式事务。
- 两平面可重建承诺不变：知识平面（Markdown）+ 事实平面（源数据 JSONL）各自可全量重建，分片布局只是物理分布，不改变重建语义。
- 若未来某 domain 内部再按 entity_id 分片，则该 domain 的编译发布需升级为"两段式 + 协调者"（先各分片本地预写，再统一 epoch 提交）——这是明确标注的复杂度跃升，默认不做。

## 7. 与远期 Raft / rqlite 的衔接

- **Raft 管副本与选主**（同数据多副本容灾 + 线性读写），**分片管数据切分**（不同数据放不同节点）。二者可组合：每个分片也可以是 Raft 多副本组。
- 落地路径建议：
  1. 先做单机 → 保持单写库 + litestream（已交付，Step 9）。
  2. 需要容灾/读扩展时：引入 rqlite 模式，WAL 兼作 Raft log，多副本 + 自动选主（MASTER-PLAN #9 远期）。
  3. 需要水平扩展写入时：才做 `domain` 一级分片，路由表 + 整-domain 迁移；再往上的 domain 内二级分片列为远期远期。
- 约定：**分片不早于 Raft 落地**；在单写库 + Raft 复制仍满足规模时，分片只会增加复杂度而无收益。
